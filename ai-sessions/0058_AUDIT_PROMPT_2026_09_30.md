`WORKSTATION_PREPARATIONS.md`. Say in the RESULT which files you read in full and which only partly, and why.

## 1. Objective

Perform a rigorous, **complete** (not sampled) analysis of all project files: documentation, architecture decisions, reverse-engineering findings, the
protocol specification, the captures, `TODO.md`, and the Android app's development. Nothing gets fixed here; everything gets found, explained with evidence,
and handed off with a concrete recommendation precise enough that a later session can act on it without re-deriving your reasoning.

## 2. Scope of the assessment — what to look for

For every file and area in scope (§3), actively identify:

1. **Errors** — technical inaccuracies, logical mistakes, incorrect Bluetooth / Android knowledge, factual errors.
2. **Inconsistencies** — contradictions within one file or across files (e.g. a protocol detail that contradicts an architecture decision; a rule in
   `PROJECT_RULES.md` or `AGENTS.md` that is violated elsewhere without acknowledgement; the same fact stated differently in two places).
3. **Improvements** — concrete opportunities to improve the architecture, documentation clarity, project structure, or reverse-engineering methodology.
4. **Incompleteness** — missing documentation, undocumented features or behaviour, dangling references, broken links, IDs not registered in
   `id_registry.csv`.
5. **Ambiguities** — vague statements, poorly defined statuses, or unclear instructions that could lead a future contributor (human or AI) to misinterpret them.
6. **Impossibilities / unworkable plans** — architecture decisions, code plans or protocol interpretations that are technically impossible, violate
   fundamental Android / Bluetooth constraints, or violate the Zero-GMS rule (`AGENTS.md` §1).
7. **Misplaced information** — content that, per the project's own structure, is in the wrong file (e.g. protocol specification in `ARCHITECTURE.md` instead of
   `PROTOCOL.md`; log analysis missing from its own `CAP-NNN-FINDINGS.md`; a finding recorded only in an `ai-sessions/` RESULT).
8. **Undiscovered protocol findings** — actively investigate what has not been investigated yet. Look at the existing `captures/`, hex dumps and protocol notes
   for patterns, opcodes, frame envelopes or correlations that were overlooked or never documented. Start from `PROTOCOL.md`'s 🔴 OPEN QUESTION and 🟡
   HYPOTHESIS entries and check them against evidence that **already exists** in `captures/` but may not have been cross-referenced (tools: `tshark`, the
   project's own `scripts/` such as `scripts/pwrpc_decode.py`). Filter every log by the Buds' address first (`AGENTS.md` §13, CLI hygiene). Report each lead
   with frame numbers, the command and the raw hex — as a lead / proposal, never as a FACT.
9. **Architectural shortcomings** — soundness of the architecture, module division, separation of concerns, dependency direction, dependency injection,
   state management, error model, testability.
10. **Application shortcomings** — in the Kotlin source (`android/app`, `android/data`, `android/domain`, `android/hardware`, `android/ui`): bugs, state
    management gaps, threading / cancellation issues, resource leaks, error handling, UI honesty (a value shown that the Buds did not report), accessibility,
    test coverage gaps (the current suite: `:data` ≈ 1567, `:hardware` 51, `:domain` 25, `:ui` 9 tests), and whether the code does what
    `ARCHITECTURE.md` / `PROTOCOL.md` / `DECISIONS.md` say it does — feature by feature, module boundary by module boundary.
11. **Search for the unknown** — an open-ended pass: what has nobody asked yet? Capabilities the official app or the protocol clearly has that were never even
    logged as a `TODO.md` candidate; ADR consequences never followed through; test-plan items that no capture has ever exercised; assumptions every document
    silently shares.
12. **Documents that are not up to date** — statements overtaken by later sessions, ADR Updates or code (e.g. a count, a status line, a "not yet built", a
    "planned" capture that has been run, a file name that changed); for each, name the newer source that supersedes it.

**Deep re-review of the sessions since the last audit/validation** (`ai-sessions/0049`/`0050`): read **in full** every prompt and result of
`0051`, `0052`, `0053`, `0054`, `0055`, `0056` and `0057`, and audit them with the same rigour as the reference documents (categories 1–7 and 12 apply
to session logs too): does each RESULT's claim (tests, frames, fixtures, "byte-identical", "approved in chat") match the files, the git history and the
captures? Are their `Status` fields and `ai-sessions/INDEX.md` rows correct?

## 4. Strict execution rules

- **No assumptions.** Verify everything, including project claims about standard protocols (Bluetooth RFCOMM, HFP, Fast Pair, pw_rpc / pw_hdlc, protobuf,
  Android APIs).
- **Validate externally.** Use the search / fetch tools to check claims against official documentation — Android Developers docs and API reference, the
  Bluetooth Core Specification and profile specifications (RFCOMM, HFP), the Google Fast Pair specification (developers.google.com/nearby/fast-pair), the
  Pigweed documentation (pw_rpc, pw_hdlc), Material 3 / Compose documentation. Cite the URL and the exact sentence (or section number) you rely on.
- **No sampling.** Do not spot-check. Perform a 100 % complete review of every file in scope (§3); check every detail. If you cannot finish a file, say so in
  the Progress block and finish it after resuming — never silently skip.
- **Best practices.** Apply industry-standard technical review methods: evidence traceability (every claim links back to a specific frame / capture /
  `file:line` / ADR sentence), structural integrity (headers and sections nest, tables match their own column definitions, cross-references resolve, IDs are
  registered), and consistency (the same fact stated the same way everywhere).
- **Run, don't guess.** Where a claim is checkable by running something read-only, run it and record the command and output: the build and test suite
  (`cd android && ./gradlew --offline --max-workers=2 assembleDebug testDebugUnitTest test lint` — keep `--max-workers=2`: an earlier session on this 15 GB
  laptop was OOM-killed while running Gradle repeatedly), `python3 scripts/lint_docs.py`, `tshark`, `scripts/pwrpc_decode.py`, `git log` / `git blame`.
  Build outputs under `android/**/build/` are not project files; generating them does not count as changing files. **Do not** run mutation tests or anything
  that edits a source file, even temporarily.
- **No file changes.** Only assess. The only file this session creates or edits is ai-sessions/0058_AUDIT_RESULT_2026_09_30.md. Do not edit
  `ai-sessions/INDEX.md` either — the maintainer updates its row when the audit is accepted. Scratch work goes into the session's scratchpad directory, never
  into the repository. No commits, no pushes.
- **Subagents** may only read and report; every finding they report is re-verified in the main session before it goes into the RESULT.

## 5. Resumability (you must be able to continue automatically after a token or rate limit)

Create ai-sessions/0058_AUDIT_RESULT_2026_09_30.md **at the very start**, with the header block of `AI_SESSION_LOG_PROCEDURE.md` §4,
`**Status:** partial — resumed`, and a **Progress** block at the top. Update the Progress block at the end of **every phase** and after every large file or
file group within a phase: which phases and files are done, which finding IDs were assigned (so numbering never collides after a resume), the last command
run, and where intermediate results live (the scratchpad directory — re-create anything that is gone; a restart wipes `/tmp`). Append each phase's findings
as soon as the phase is done.

A resumed session (`AI_SESSION_LOG_PROCEDURE.md` §5 — the same number, the same file, never a new session number) re-reads this prompt, then the RESULT's
Progress block, and continues from the first unfinished step. It never redoes a finished, recorded step and never assumes an unrecorded step was done.
Set `**Status:** complete` only when every phase in §6 is finished.

## 6. Phases (strictly sequential; do not start a phase before the previous one is finished and recorded)

0. **Set-up** — create the RESULT (§5); record `git log -1`, `git status --short`, `git fetch && git log --oneline HEAD..origin/main`; the mandatory reading
   (§0); run the build/test/lint gate and `scripts/lint_docs.py` once as the factual baseline for later phases.
1. **Governance / compliance** — `AGENTS.md`, `PROJECT_RULES.md`, `PROJECT.md`, `AI_SESSION_LOG_PROCEDURE.md`: internal consistency, and whether the rest of
   the project complies with them (ADR sign-off provenance per `AGENTS.md` §6; the minimal permission set and the manifests per §2; Zero-GMS per §1;
   dependency policy per §10 against `libs.versions.toml` and every `build.gradle.kts`; logging rules per §9; AGPL headers per §12; evidence labels per
   `PROJECT_RULES.md` §1).
2. **Protocol** — `PROTOCOL.md` end to end: internal consistency (does a later Update contradict an earlier FACT without flagging it?), label correctness,
   every cited frame spot-verified **for every FACT** (not a sample), then the §2 item 8 investigation of 🔴 / 🟡 entries.
3. **Captures** — every `CAP-NNN-EVENT-NOTES.md` / `CAP-NNN-FINDINGS.md`: traceability of each finding to frames, consistency with `PROTOCOL.md`, test-plan
   traceability (`AGENTS.md` §13 item 7), `PROJECT_RULES.md` rule 9a (findings rewritten in place, not accumulating addenda), registration in
   `id_registry.csv`; planned captures (skeletons) checked for the build and steps they claim.
4. **Architecture** — `ARCHITECTURE.md` end to end against the actual source tree: does the code implement what it claims, module by module, feature by
   feature (§5a's table row by row)?
5. **Decisions** — every ADR: internal consistency, proper superseding (vs. silent contradiction), whether each ADR's Consequences were followed through in
   code and documents, `id_registry.csv` integrity.
6. **Backlog and housekeeping** — `TODO.md`, `CHANGELOG.md`, `README.md`, `id_registry.csv`, `ai-sessions/INDEX.md`, `APP_TESTPLAN.md`,
   `TESTPLAN_BLUETOOTH_HCI_SNOOP.md`: staleness (§2 item 12), dangling references, items marked done that are not (and vice versa), duplicates, conflicts.
7. **Session history** — the whole `ai-sessions/` set structurally, and `0051` … `0057` in full (§2).
8. **Application** — every Kotlin file (main and test), Gradle configuration and manifest: §2 items 9–10, code-versus-documentation fidelity, tests versus
   `AGENTS.md` §11 (real capture bytes as fixtures, fuzz tests for every `FrameDecoder`, no hand-built fixture without a real one beside it).
9. **Synthesis** — the open-ended "search for the unknown" (§2 item 11); deduplicate findings that surfaced in more than one phase and cross-reference them;
   assign final severities; write the executive summary and the prioritised action list (§8).

## 7. Exclusions

**Privacy is out of scope.** Do not scan for, flag or report privacy-related data such as leaked MAC addresses, e-mail addresses, names or other personal
identifiers — ignore this category entirely. Real identifiers in `captures/CAP-NNN-*` are the maintainer's own informed decision (`DECISIONS.md` ADR-010).
(This exclusion covers the audit's findings; it does not license breaking `AGENTS.md`'s operational rules during the session.)

## 8. Deliverables

A comprehensive, clearly structured audit report in ai-sessions/0058_AUDIT_RESULT_2026_09_30.md (header and status per `AI_SESSION_LOG_PROCEDURE.md` §4),
in this order:

1. **Progress** block (§5).
2. **Executive summary** in plain language: the state of the project, the most important findings, and what should be done first.
3. **Method:** what was read in full / partly (and why), every command run (with its result), every external source consulted (URL + exact sentence).
4. **Findings**, grouped logically — by the categories of §2 or by file/area, whichever reads better once you see what you found; state which grouping you
   chose and why. Give every finding a stable ID (e.g. `A58-GOV-01`, `A58-PROT-07`, `A58-APP-12`). **For every finding include:**
   - the exact file and location (`file:line` or section; a frame number for capture-based findings), with the quoted text or bytes;
   - why it is a problem — which §2 category (or categories) and the reasoning — and its evidence label (FACT / HYPOTHESIS / ASSUMPTION / OPEN QUESTION);
   - **how you verified it** (the command, the file you opened, the frame you decoded);
   - a concrete, actionable recommendation for how to fix or resolve it — precise enough to act on without re-deriving your reasoning; where a fix needs a
     FACT promotion or an ADR, say so and give the draft text, labelled as a proposal awaiting the maintainer's sign-off (`AGENTS.md` §6);
   - where applicable, the external evidence or documentation that validates the finding (URL + section / exact sentence);
   - a **severity**: *critical* (breaks correct operation, risks the hardware or violates a hard guardrail), *major* (wrong behaviour, a wrong FACT, a
     broken decision chain), *minor* (inconsistency, staleness, missing reference), *nit* (wording, formatting).
5. **Undiscovered protocol leads** (§2 item 8) in their own section: per lead the frames, the command, the raw hex, the proposed reading, its label and the
   capture or experiment that would confirm or refute it.
6. **Prioritised action list:** every finding ID in the order the maintainer should handle it, grouped by severity, with the kind of session each needs
   (MAINTENANCE / FEATURE / CAPTURE / REVIEW) and which ones need a maintainer decision first.
7. **Statistics:** findings per category and per severity; files reviewed; what could not be verified and why.

When the report is complete, set `**Status:** complete`, then give the maintainer a short summary in chat (the number of findings per severity and the top
five actions). Do not commit or push; the maintainer decides what happens next.
