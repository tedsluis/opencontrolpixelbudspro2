## 3. Preliminary observations by the author of this prompt (**unverified leads — verify each before relying on it; never copy them into a result as facts**)

Read from the app's debug export only (no video, HCI or system-log analysis was done by the prompt author):

1. **Permissions work.** 17:17:25 *"Permissions: showing the system prompt"* → 17:17:31 both granted. (Plausibly the fix from `0041` — confirm on video.)
2. **Pairing.** 17:17:41.507 and .589: two *"association requested (CDM picker)"* 82 ms apart, then *"association failed (More than one AssociationRequests are processing.)"* — a double tap or a double invocation → needs a guard. 17:17:48 *"association created"*, *"device resolved from the association's own device"* (so the `getAssociatedDevice()` path works), *"createBond()"*; 17:17:50 a *second* pairing attempt *"reusing existing association (1 total)"* and *"already bonded — no createBond()"* (association reuse and the already-bonded path work); but **17:18:33 *"Pairing: bond timed out"*** — 45 s after `createBond()`, although Android bonded the device (HFP state changes at 17:17:49/17:17:50) — and there is **no** *"bond state BONDING/BONDED"* line at all. Hypothesis: the bond-state receiver, registered with `RECEIVER_NOT_EXPORTED`, **never receives the system `ACTION_BOND_STATE_CHANGED` broadcast** on this device, so a successful pairing is reported as a timeout. (Also: the timeout coroutine is not cancelled when the flow is superseded/finished.)
3. **`OsConnectionObserver` (Android-state mirroring) may not receive live broadcasts.** All its lines read `Android link (): …` — the reason text is **empty** (a `$reason` was expanded by the shell while the file was generated: a cosmetic bug in the log line). More important: between 17:20:19.939 (observer started, `NOT_CONNECTED`) and 17:20:28.276 (stopped) the *HFP* receiver (registered **without** the flag) logged two `CONNECTION_STATE_CHANGED` broadcasts (17:20:25.735, 17:20:26.178) — the Buds reconnecting to Android — yet the observer logged **no** re-evaluation. The observer only shows `CONNECTED via profiles [1, 2]` after being *re-started* (17:20:36, 17:21:06, 17:23:31, 17:24:48) — i.e. the initial proxy read works, live updates via the non-exported receiver do not. Hypothesis: `RECEIVER_NOT_EXPORTED` blocks (some) system Bluetooth broadcasts on GrapheneOS/Android 17; the fix candidates are `RECEIVER_EXPORTED` for protected system broadcasts, or re-reading state on lifecycle resume plus profile-proxy callbacks. The 16:56 screenshot ("Android doesn't show the Buds as connected (yet)" while the Bluetooth icon is in the status bar and the session is `Ready`) is consistent with a stale/wrong link state.
