## Purpose and scope

This is a **read-only review**, not an analysis or implementation task. Its job is to independently
re-verify, from the raw evidence, every claim this project has already recorded about its Bluetooth
captures — not to produce new protocol knowledge, and not to fix anything it finds wrong.

**Target: every capture session under `captures/CAP-NNN-*/` that has actual recorded data** — i.e.
every `CAP-NNN` whose `CAPTURE_BLUETOOTH_HCI_SNOOP.md` §9 Capture Index row is **not** `planned`
(check the Status column and the folder's own contents — a `planned` row has no log/video files and
cannot be reviewed). At the time this prompt was written that is **45 of 52** registered captures
(`CAP-030`, `CAP-043`, `CAP-044`, `CAP-047`, `CAP-050`, `CAP-051`, `CAP-052` are `planned` — skip
them; re-derive the exact current list from `CAPTURE_BLUETOOTH_HCI_SNOOP.md` §9 at execution time,
since it may have changed since this prompt was written).

**This will not fit in one session.** 45 captures, each requiring a full-duration log re-decode, a
full-duration video re-watch, an APK cross-reference pass, and an internet-validation pass, is a
multi-session task by construction — plan for that from the start (see "How to (re)start this
prompt" below), the same way `ai-sessions/0010_CAPTURE_PROMPT_2026_09_12.md` did for its own
(much smaller) 8-capture scope.

## How to (re)start this prompt — read this paragraph first, every time

Before anything else: check whether `ai-sessions/0011_REVIEW_RESULT_2026_09_12.md` already exists.
- **It does not exist** → this is the first run. Create it in Phase 0 with a per-capture status
  table (one row per `CAP-NNN` in scope, see Phase 0 below) and start working through captures in
  the priority order given there.
- **It already exists** → read it in full. Its per-capture status table says which captures are
  already `done`. Skip straight to the first `not started` (or `partial`) row and continue from
  there — do not redo a `done` capture's review. You still owe the full "Mandatory reading order"
  below in this session, resumption or not, since a new session has no memory of a previous one.

Before ending a turn (the review is done, or a rate limit / context limit is approaching), update
`0011_REVIEW_RESULT_2026_09_12.md`'s status table and its `Status` header field
(`partial — resumed` while incomplete, per `AI_SESSION_LOG_PROCEDURE.md` §4/§5) so the next session
picks up cleanly. Do not leave a capture half-reviewed without a note describing exactly what was
and wasn't checked.

## Guardrails — read together with `AGENTS.md` §6/§15, not a substitute for them

- **This review changes nothing.** Do not edit `CAPTURE_BLUETOOTH_HCI_SNOOP.md`,
  `TESTPLAN_BLUETOOTH_HCI_SNOOP.md`, `PROTOCOL.md`, `DECISIONS.md`, `REVERSE_ENGINEERING.md`, any
  `CAP-NNN-FINDINGS.md`/`CAP-NNN-EVENT-NOTES.md`, `id_registry.csv`, or any other project file. The
  **only** file this prompt writes to is its own `ai-sessions/0011_REVIEW_RESULT_2026_09_12.md`.
  If, while reviewing, an actual error is found (a wrong frame number, a miscited file+line, a
  mislabeled FACT/HYPOTHESIS status, a broken cross-reference), **do not fix it** — record it as a
  finding, per the Output format below, for the maintainer to act on afterward.
- **Never promote anything to 🟢 FACT, and never draft or alter a `DECISIONS.md` ADR** — this review
  doesn't touch `DECISIONS.md` at all (see above), but the same principle extends to this review's
  own language: report what the evidence shows, don't upgrade a capture's own HYPOTHESIS-level
  finding to a firmer status just because this review's own re-check happened to agree with it.
- **No assumptions, no guessing.** Every finding in the RESULT file must trace to a command you
  actually ran and its actual output (the hex-and-script rule, `PROJECT_RULES.md` rule 4a) or a
  specific frame extracted from the actual video file, or a specific, quoted line from an actually-
  fetched external page, or a specific file+line actually read in the decompiled APK. If something
  can't be verified, say so explicitly ("not verifiable from available evidence") — never fill the
  gap with a plausible-sounding guess (`AGENTS.md` §13.6).
- **No sampling, at any level.** Not which captures get reviewed (all 45, not a subset "representative
  sample"), not which parts of a given log get decoded (every DLCI 0x02/0x04/0x08 frame the
  capture's own `CAP-NNN-FINDINGS.md` cites, plus a full census of the log to check nothing else was
  silently missed), not which parts of a given video get watched (full duration, dense frame
  extraction, tightened around every claimed event timestamp).
- **The APK cross-reference step stays within `DECISIONS.md` ADR-017's mechanical-assistance
  boundary**: search, list, and explain already-recovered classes/fields/call sites; verify that an
  existing citation (file+line, a claimed log message, a claimed field number) actually says what
  it's claimed to say. Do **not** decide that a newly-noticed class/field is relevant to a claim
  that didn't already cite it, and do not propose a new HYPOTHESIS — that judgment call belongs to
  the maintainer, not to this review.
- **Never reproduce Google's own source code verbatim** in the RESULT file beyond the minimum needed
  to cite a finding (a class/method name, a short log-message string, a field number) — describe,
  don't paste large blocks (`AGENTS.md` §12).
- **MAC addresses**: this project's own captures intentionally retain real MAC addresses
  (`DECISIONS.md` ADR-010) — citing one in a finding is normal here, not a violation to flag.

## Methodology — apply this to every capture in scope

### Step 1 — Orient
Read the capture's own `CAP-NNN-FINDINGS.md`, `CAP-NNN-EVENT-NOTES.md`,
`CAPTURE_BLUETOOTH_HCI_SNOOP.md` §9's row for it, and every `TESTPLAN_BLUETOOTH_HCI_SNOOP.md`
Test-ID row whose Evidence column points at it. List every factual claim made: every frame number,
every hex byte sequence, every timestamp, every FACT/HYPOTHESIS/ASSUMPTION/OPEN QUESTION label,
every cross-reference to another capture, ADR, or `PROTOCOL.md` section.

### Step 2 — Full, independent log re-verification (tshark, no sampling)
For the capture's actual `CAP-NNN-btsnoop_hci.log` (and `.log.last`/`-combined.log` if present —
check which one the capture's own `FINDINGS.md` says it used, and verify that determination is
still sound; do not just trust it, re-derive it the way `CAP-040-FINDINGS.md` §0 /
`CAP-042-FINDINGS.md` §0 / `ai-sessions/0010_CAPTURE_RESULT_2026_09_12.md`'s own `CAP-048`/`CAP-049`
entries did):
- `capinfos`: packet count, duration, first/last timestamp, confirm the claimed truncation status
  (`cap_len==len` for every frame) independently, not by trusting the file's own prose claim.
- CLI hygiene per `AGENTS.md` §13: enumerate every Bluetooth address in the log before any
  protocol-specific filter, confirm the Buds' own classic address matches what the capture's own
  metadata claims.
- Re-run **every** `tshark`/Python decode command the capture's `FINDINGS.md` cites, against the
  **actual current file**, and confirm the output matches what's written — byte for byte, frame
  number for frame number. Flag any mismatch, however small.
- Beyond re-running cited commands: do a full DLCI census (`btrfcomm.dlci` value counts) and a full
  scan for `08 11`/`08 12`/`08 13` (DLCI 0x04 ANC opcodes), `field5{field4{...}}` shapes (DLCI 0x02
  settings writes), and `[Group][Code][Length]` frames (DLCI 0x08) across the **entire** log — not
  just the windows the existing `FINDINGS.md` already discusses — to check whether anything is
  silently undocumented that should have been flagged as an `UnidentifiedFrame`-class finding per
  `AGENTS.md` §6's own philosophy.

### Step 3 — Full, independent video re-verification (ffmpeg, no sampling)
- `ffprobe` the actual `CAP-NNN-recording.mp4` for its real duration/resolution — confirm it matches
  what the capture's own metadata table claims.
- Extract frames across the **entire** video duration (dense enough that no on-screen state change
  could be missed between two consecutive frames — tighten to sub-second spacing around every
  timestamp the `FINDINGS.md`/`EVENT-NOTES.md` cites as evidence for a claim).
- For every claimed video-correlated timestamp in the existing documents, extract the frame at that
  exact wall-clock overlay time and confirm the screen actually shows what's claimed.

### Step 4 — Cross-checks
- Does every frame number and hex byte sequence cited in `CAP-NNN-FINDINGS.md` actually exist, at
  that frame number, in the actual log, with that actual content? (This is the single most
  important check in this review — it is exactly what `ai-sessions/0008` found broken at scale for
  a different document.)
- Does `PROTOCOL.md`'s own restatement of this capture's finding (wherever it cites `CAP-NNN`)
  accurately reflect what the capture's own `FINDINGS.md` says? Flag any drift.
- Does `DECISIONS.md`'s ADR citing this capture (if any) accurately reflect it?
- Does `CAPTURE_BLUETOOTH_HCI_SNOOP.md` §9's row for this capture (dates, firmware, app version,
  Test-IDs, outcome summary) match the capture's own `EVENT-NOTES.md`/`FINDINGS.md`?
- Does `TESTPLAN_BLUETOOTH_HCI_SNOOP.md`'s Evidence-column pointer for every Test-ID this capture
  claims to exercise actually resolve to a real section in the cited `FINDINGS.md`?
- Where two or more captures make overlapping or related claims (e.g. multiple captures document
  the same DLCI 0x08 message, or the same ADR-024 dock-state behavior), do their claims agree with
  each other? Flag any unreconciled tension, per `PROJECT_RULES.md` rule 1 — don't resolve it
  yourself, report it.

### Step 5 — APK cross-reference (within ADR-017's boundary — verify, don't newly decide relevance)
For every claim in this capture that cites, or is cited by, a `REVERSE_ENGINEERING.md` entry (a
`qhr` field number, a class/method name, a logged string like `"Set device Multipoint as: %s"`):
search the actual decompiled workspace (`reverse-engineering/apk/<version>/jadx-output/`, falling
back to `apktool-output/` only where JADX is unreadable, per `APK_REVERSE_ENGINEERING_PROCEDURE.md`)
and confirm the cited file+line actually exists and actually contains the claimed code/string. Flag
any citation that doesn't resolve, resolves to different content than claimed, or resolves to
unrelated code — exactly the class of error `ai-sessions/0008` found in bulk in a different
session's own APK citations.

### Step 6 — External validation
For any wire finding that maps to a publicly documented standard or spec (Fast Pair message
groups/codes, HFP AT commands, Bluetooth SIG assigned UUIDs/service names, Pigweed `pw_hdlc`/
`pw_rpc`), fetch the actual current spec page and quote the specific passage the claim rests on —
following `DESKRESEARCH_FINDINGS.md`'s own established citation pattern. Note explicitly if a
previously-cited page no longer says what it's claimed to say (specs can be revised), and note if a
claim has never actually been checked against an external source at all despite being eligible for
it.

### Step 7 — Consistency checks
- Is every FACT/HYPOTHESIS/ASSUMPTION/OPEN QUESTION label in this capture's `FINDINGS.md` actually
  justified by the evidence bar `PROJECT_RULES.md` rule 1 sets for that tier? Flag anything that
  reads more confident than its own cited evidence supports (or, separately, anything that reads
  more tentative than strong evidence would justify — under-claiming is also worth flagging, not
  just over-claiming).
- Is `id_registry.csv`'s row for this `CAP-NNN` accurate (status, one-line description)?
- Does the capture's folder name (`CAP-NNN-YYYY-MM-DD_HH-MM-SS_HH-MM-SS-Group_X`) match its own
  log/video's actual start/end timestamps?

## Output format — required for every finding

The `RESULT` file must report findings as a flat, numbered list (grouped under each capture's own
subsection), **one entry per issue or confirmation**, each with exactly these four fields, in this
order:

```
### Finding <N> — <one-line summary>

- **Finding:** what was found (a discrepancy, a confirmed-correct claim, a broken cross-reference,
  an unlabeled/mislabeled confidence tier, a missed decode, etc.) — state it as a fact about what
  the evidence shows, not as an opinion.
- **Evidence:** the exact command run and its actual output, or the exact frame/timestamp extracted
  and what it shows, or the exact external page URL and the quoted passage, or the exact file+line
  read in the APK workspace. Enough for someone else to independently reproduce the check.
- **Advice:** a concrete, specific recommendation (e.g. "correct `CAP-NNN-FINDINGS.md` §M's frame
  number from X to Y"; "no action needed, claim confirmed exactly as stated"; "this needs a
  maintainer decision, not a mechanical fix, because..."). If the finding is a clean confirmation
  with nothing to change, say so plainly — a confirmation is still a reportable finding, not a
  non-event, since it's positive evidence the existing document is trustworthy at that point.
- **Location:** exactly where the finding was found — the specific document + section, or capture +
  frame number, or APK file + line, being reviewed. (This is *where the underlying claim being
  checked lives*, not a repeat of the Evidence field's own command output.)
```

Report **every** check performed, not only the ones that turned up a problem — a review that only
lists problems gives no way to distinguish "this wasn't checked" from "this was checked and found
correct." Confirmations and discrepancies are both required output, per `PROJECT_RULES.md` rule 12's
own "a failed or inconclusive test is still recorded" principle extended to this review's own
checks.

Complete the Mandatory reading order above. Enumerate the actual current capture list from
`CAPTURE_BLUETOOTH_HCI_SNOOP.md` §9 (excluding `planned` rows). Create
`ai-sessions/0011_REVIEW_RESULT_2026_09_12.md` with the required header block

per `CAP-NNN` in scope (`not started` / `partial` / `done`), plus a running count of findings by

**Suggested priority order** (not mandatory — cover all of them eventually, but front-load the
highest-leverage ones first in case of a rate-limit/session cutoff): captures cited by the most
`DECISIONS.md` ADRs first, then captures already flagged elsewhere as having open/unreconciled
tensions (e.g. anything `ai-sessions/0010_CAPTURE_RESULT_2026_09_12.md`'s own synthesis names), then
the remainder in `CAP-NNN` order.

## Phase N — One phase per capture (or a small batch per turn)

Apply the full Methodology (Steps 1–7) to each capture in scope. Update
`0011_REVIEW_RESULT_2026_09_12.md`'s status table and append that capture's findings (per the
Output format above) before moving to the next one — this is the checkpoint a resumed session reads.

## Final phase — Wrap-up

- Re-read every capture's own findings section for cross-capture patterns (does the same kind of
  discrepancy recur across multiple captures — e.g. a systematic frame-number drift, a recurring
  mislabeling pattern — worth calling out as a single higher-level finding rather than N separate
  ones)?
- Write a short executive summary at the top of the RESULT file: total captures reviewed, total
  findings by type (confirmed-correct / discrepancy-minor / discrepancy-major / needs-maintainer-
  decision), and the single most important thing for the maintainer to look at first.
- Set `Status: complete` once every in-scope capture has a `done` row and the executive summary is
  written. This review produces no FACT promotions and no ADRs by design (see Guardrails), so
  `Status` does not need an `awaiting maintainer sign-off` state the way `ai-sessions/0010`'s own
  RESULT did — its output is itself the deliverable for the maintainer to act on.
