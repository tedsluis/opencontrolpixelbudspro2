### `esk` — per-case table

`esk` implements a 2-argument functional interface (`Object apply(Object)`-shaped via `pkl`/similar,
called as `esk.a(Object obj)`), discriminator field `c`, 20 cases (`packed-switch`, labels
`pswitch_13`…`pswitch_0`) + 1 default, **all JADX-decompilable** (unlike `aie`). Cross-referencing
every constructor call site (`grep -rn "new esk(" jadx-output/sources/defpackage/`) recovered a
concrete real-world caller for all 20 real discriminators **and** the default branch (a genuine
`new esk(this, gwvVar, 20, null)` call exists at `gcp.java:51` — discriminator `20` is outside the
enumerated `0-19` range, so it legitimately falls through to the default branch; this is not a gap
in the tool's own case enumeration, it is a real call site deliberately using the shared "no matching
case" behavior).

**Headline structural finding, not previously documented anywhere in this project:** the large
majority of `esk`'s cases are **not Maestro/Bluetooth code at all** — they are the companion app's
bundled copy of **AndroidX WorkManager's own Room-generated DAO implementation**
(`androidx.work.impl.model.WorkSpecDao`/`WorkTagDao`/`WorkProgressDao`, R8-obfuscated to
`ess`/`esc`/`esv`/`esf`/`gos`/`ejv`/`qa`). This is not inference from naming alone — it is confirmed
by literal, unobfuscated SQL text still present in the decompiled source: `"SELECT `progress`,
`work_spec_id` FROM `WorkProgress` WHERE `work_spec_id` IN (...)"` (`ess.java:59`'s `G()` method),
`"SELECT `tag`,`work_spec_id` FROM `WorkTag` WHERE `work_spec_id` IN (...)"` (`ess.java:96`'s `H()`
method), `"SELECT * FROM workspec WHERE id=?"` (`ess.java`'s `c()` method), and `esf.java`'s own log
tag `ems.a("WorkSpec")` — `WorkSpec`/`WorkTag`/`WorkProgress` are the exact, well-known table names
of `androidx.work.impl.WorkDatabase` (public AndroidX WorkManager source, referenced here only as a
naming fact to explain what the decompiled SQL text matches, not as a code source consulted).

### 3.3 Sketch: first, narrowest useful version of the structural code index

## Phase 4 — What workflows does APK reverse engineering in this project need?

### 4.1 The existing documented workflow

`APK_REVERSE_ENGINEERING_PROCEDURE.md` documents a single linear flow, **pull → decompile → search →
analyze**, with one named-but-not-yet-implemented extension:

1. **Pull** (§2): find package/version, pull base+split APKs via `adb`, hash, record in
   `reverse-engineering/APK_VERSIONS.md`.
2. **Diff-against-previous-version pass** (§2.1) — *named but not yet run in practice*, since only one
   APK version has ever been analyzed (confirmed again this session, Phase 0). Its own steps (DEX
   class-list diff, re-check every existing `REVERSE_ENGINEERING.md` finding against the new version)
   are already written down, just never exercised.
3. **Decompile** (§3): `jadx`+`apktool`+`pbtk` (the last one a confirmed structural dead end for this
   app's codegen, per `TODO.md`'s Phase 2 checklist).
4. **Keyword search** (§4): manifest-first, string-literal search, `pbpctrl`-docs cross-check, keyword
   list, exclusion list, present-candidates-to-maintainer.
5. **Analysis approach** (§5): write up in `REVERSE_ENGINEERING.md` with FACT/HYPOTHESIS labels, note
   a hypothesis test, promote to `PROTOCOL.md` only after capture correlation, maintainer sign-off
   gate for FACT/ADR.

### 4.2 Where `lambda_dispatcher_resolver` fits — a concrete addition

**Exact proposed wording**, as a new numbered step inserted into §4 ("Keyword Search and
Search-Efficiency Techniques"), between the existing steps 4 and 5:

### 4.4 Steps and tool support per workflow

| Workflow | Steps | Tool support |
|---|---|---|
