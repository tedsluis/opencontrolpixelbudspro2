## 0. Summary for the maintainer (plain language)

Most of the project is careful and well evidenced. The Android app does what the captures say it does. But this audit found
**four problems that matter for correct operation**, plus a lot of documentation that no longer matches the code or the latest
decisions.

1. **The Case battery can't work as built, and the 🟢 FACT behind the last fix is wrong (finding CAP-1, severity S1).**
   `ai-sessions/0043` promoted "the Buds push the Case level without the phone-side `0e 04` request" to 🟢 FACT. ADR-038's retry
   rests on that claim. The `CAP-060` wire log shows the opposite for every push that comes right after a channel opens. Each one
   is preceded by Google Play services sending `0e 04 00 00` (frames 1284→1307, 1979→1993, 2279→2310, 4830→4856, 5015→5041,
   5149→5168, 5828→5856). The app's own receive-only claims held DLCI 0x08 open for about 2.4–2.8 s and received **nothing**
   (frames 3770–3783, 4221–4246, and the app log's four `connected … Timeout … released` sequences). That is a timeout with the
   channel still open, not contention, so ADR-038's retry never fires in that case. `ai-sessions/0042` §12(h) had already stated
   the right conclusion: if the result is Timeout every time, the next step is an ADR to send `0e 04`.
2. **ANC "Set" frames carry a message nonce and MAC, not 16 "reserved" bytes (finding PR-MAC, S2, newly found).** The official
   Fast Pair MAC spec says a MAC-protected message ends with an 8-byte message nonce and an 8-byte MAC. The Buds send the session
   nonce (`03 0a 00 08 …`) every time DLCI 0x04 opens. The project never identified that message. The official app's Set frames
   carry 16 random-looking bytes; the app sends 16 zero bytes. The Buds accept them anyway (`CAP-059` frames 2768→2779→2782).
   The spec says the Buds should NAK. So ANC works today only because this firmware does not check the MAC. A firmware update
   that starts checking would silently break ANC switching.
3. **The Startup Handshake / Safe Mode doesn't exist in code (finding APP-1, S2).** `ARCHITECTURE.md` §8.1 describes it, the
   README's bricking disclaimer relies on it, and ADR-012 and ADR-036 depend on it. Nothing ever produces `UnsupportedFirmware`.
   The app sends ANC, EQ and Ring writes regardless of firmware, and never checks the Fast Pair Model ID (`da 2d b1`) either.
4. **The app's own state handling has concrete defects (APP-2 … APP-6, S2).**
   - The DLCI 0x04/0x08 stream splitters are never reset between claims, so a frame cut off by a contended channel can
     permanently misalign later frames.
   - User actions run in the Activity's composition scope, so a rotation during Connect can leave the state stuck at
     "Connecting", with no button.
   - When the Buds don't answer an ANC Set, the app still shows the requested mode as "updated".
   - The dock-state line ignores ADR-024's "may be stale for 1–2 s after a (re)open" consequence.
   - The foreground-service notification is not stopped when the session ends while the app is in the background.

Also found:
- **Leads from existing evidence:** the spec defines a **local "ring both"** value (`0x03`), which ADR-027's permanent non-goal
  never tested. The HID surface is Android's standard **Head Tracker HID protocol** (spatial audio), which answers
  `ARCHITECTURE.md` §15's only open question. `PROTOCOL.md` §5.2's one "mid-connection" counter-example is actually a
  **fresh ACL connection** (handle reuse), so the "DLCI 0x02 opens last" pattern has a real counter-example.
- **Housekeeping:**
  - The CI docs linter fails on `main` (exit 1).
  - There is no CI build of the app.
  - An 11.7 MB system log was committed outside Git LFS.
  - The HFP removal was never recorded as an ADR.
  - README, `ARCHITECTURE.md` §1/§3/§4/§5/§13, `PROTOCOL.md` §2.3/§4.1-status/§4.2-status/§4.3-intro/§6, `TODO.md` and
    `id_registry.csv` carry many stale statements that now contradict later ADRs.

**Grouping chosen:** findings are grouped **by area, in the prompt's phase order** (§1 governance … §8 app), because most defects
are "document X no longer matches decision/code Y", and a later fixing session will work file by file. Each finding has an ID,
a severity and a label, and §9 gives a cross-area priority list.

**Severity scale:** **S1** = blocks or falsifies correct operation or a recorded FACT · **S2** = significant defect, risk or rule
violation · **S3** = documentation inconsistency/staleness that can mislead a future session · **S4** = nit/clarity.

**Evidence labels** follow `PROJECT_RULES.md` §1: 🟢 FACT (checked directly: frame, file:line, fetched spec text), 🟡 HYPOTHESIS
(with a test), ⚪ ASSUMPTION, 🔴 OPEN QUESTION.
