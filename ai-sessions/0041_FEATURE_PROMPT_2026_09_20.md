### Preliminary observations by the author of this prompt (**unverified leads — verify each before relying on it; never copy them into a result as facts**)
1. **Pairing is built in** (`BudsCompanionPairing`, `ai-sessions/0035`/`0036`). The system log for test 2 shows Companion Device Manager **succeeding** every time: `onAssociationApproved() macAddress=<the Buds' address>`, `Adding new association=[Association{mId=26/27/28 …, mDeviceMacAddress=<same address> …}]` at 07:25:48, 07:27:19 and 07:27:32 UTC, each preceded by `onDeviceFound() … 'Pixel Buds Pro 2 <owner>' - New device`. So the failure is **after** CDM, in the app. No bond-state/`createBond` lines appear in the retained log window (the log's Bluetooth-stack coverage is short, so this is weak evidence).
2. **Leading suspect for "could not resolve the selected device":** `BudsCompanionPairing.deviceForAssociation()` calls `adapter.getRemoteDevice(info.deviceMacAddress.toString())`. `android.net.MacAddress.toString()` is **lower-case** (`xx:xx:xx:cf:6e:07` style, exactly as logged), while `BluetoothAdapter.getRemoteDevice(String)` requires **upper-case** hex and throws `IllegalArgumentException` otherwise — which the code catches and turns into `null` → that exact message. Verify against the SDK (`compileSdk 34`); prefer `AssociationInfo.getAssociatedDevice()?.bluetoothDevice` (API 34) or upper-casing the address.
3. **Leading suspect for "already paired but the app says not paired":** the app **never requests any runtime permission** (a grep for `requestPermissions`/`RequestPermission`/`checkSelfPermission` finds nothing; the manifest only *declares* `BLUETOOTH_CONNECT` and `POST_NOTIFICATIONS`). Clearing app data resets runtime permissions, so `BluetoothAdapter.bondedDevices` throws `SecurityException`, which `BudsCompanionPairing.bondedDevice()` swallows into `null` — indistinguishable from "nothing paired". The same missing grant would make `OsConnectionObserver` (0039) unable to see Android's connection state (`BluetoothProfile.getConnectedDevices()` also needs `BLUETOOTH_CONNECT`) and would hide the foreground-service notification (`POST_NOTIFICATIONS`). In test 1 the permission was evidently granted, so *that* run's "Disconnected while Android is connected" has a different or additional cause — check `OsConnectionObserver`, `bondedDevice()`'s name-substring match, and what the Connection card actually showed.
4. **Every CDM association attempt created a new association** (ids 26, 27, 28). The app never reuses or cleans up existing ones (`getMyAssociations()`).
5. The app's logcat for test 2 contains **no `OpenControlBuds` lines at all** — the pairing/permission path has **no `BleLogger` logging**, which is why the failure was invisible (`AGENTS.md` §13.3 requires logging around pairing).
6. **EQ inaudible — leads:** (a) our EQ write frames use the constant header captured in `CAP-015` (`channel_id 19`, HDLC address per `Hdlc.encode(address = 0x0000, control = 0x3b, …)`, marked `TODO(verify)` in `BudsRepositoryImpl`), while a fresh connection's unsolicited packet from the Buds and `CAP-036`'s official reads use `channel_id 21` (`DESKRESEARCH_FINDINGS.md` 2026-09-19, open items 1–3); the Buds may be silently rejecting our requests (`pw_rpc` `CLIENT_ERROR`/`NOT_FOUND`). (b) The app logs only inbound DLCI 0x02 bytes in Debug mode and does not interpret responses, so a rejection would never have been noticed. Verify from the captures and the code; do not assume.
