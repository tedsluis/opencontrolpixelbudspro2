## 2. Scope of the assessment — what to look for

For every file and area in scope (§3), actively identify:

1. **Errors** — technical inaccuracies, logical mistakes, incorrect Bluetooth / Android knowledge, factual errors.
2. **Inconsistencies** — contradictions within one file or across files (e.g. a protocol detail that contradicts an architecture decision; a rule in
   `PROJECT_RULES.md` or `AGENTS.md` that is violated elsewhere without acknowledgement; the same fact stated differently in two places; an ADR Update whose
   consequence a pointer note in `AGENTS.md` records but another document does not).
3. **Improvements** — concrete opportunities to improve the architecture, documentation clarity, project structure, or reverse-engineering methodology.
4. **Incompleteness** — missing documentation, undocumented features or behaviour, dangling references, broken links, IDs not registered in `id_registry.csv`,
   a capture or session referenced but not indexed.
5. **Ambiguities** — vague statements, poorly defined statuses, or unclear instructions that could lead a future contributor (human or AI) to misinterpret them.
6. **Impossibilities / unworkable plans** — architecture decisions, code plans or protocol interpretations that are technically impossible, violate
   fundamental Android / Bluetooth constraints, or violate the Zero-GMS rule (`AGENTS.md` §1).
7. **Misplaced information** — content that, per the project's own structure, is in the wrong file (e.g. protocol specification in `ARCHITECTURE.md` instead of
   `PROTOCOL.md`; log analysis missing from its own `CAP-NNN-FINDINGS.md`; a finding recorded only in an `ai-sessions/` RESULT or only in `DESKRESEARCH_FINDINGS.md`).
