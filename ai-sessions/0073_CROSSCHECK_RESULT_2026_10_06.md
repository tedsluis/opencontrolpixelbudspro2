## Answers in plain language

**1. Is what the project wrote down about the official app correct?** Almost all of it. The project's documents point 968 times at a file (and
usually a line) of the decompiled app. Every one of those was checked: 644 hold exactly what the sentence says, 300 name a file without a line
and the file exists, 19 are names of Android or protobuf source files (not this app). Five were off — three pointed a few lines too high or low,
two pointed at the wrong method — and three counts were inexact. None of the eight changes a protocol finding. They are corrected with a dated
line under each entry of `REVERSE_ENGINEERING.md`. The register's schema claims (807 message schemas, the 38 settings of `qhr`, the response
messages), its "there is exactly one such class" claims and its "this string occurs nowhere" claims were re-run with the tools: all confirmed.

**2. What do the registers hold now?**
- *Every MAESTRO service and method the Buds and any app ever used on the wire has a name* — 8 services and 16 methods in 80 logs
  (21,692 packets). The two ids that were still unnamed after `CAP-069` are `a10a20.kpi.Kpi` / `KpiStream` and `maestro_pw.JitterBuffer` /
  `SetJitterBufferSizePreference`. Both names are in the **old** app version; the newer app only *uses* them. The app's whole catalogue (15 services)
  is listed, including the ones never seen on a wire (eartip fit test, head-gesture detection, forced Multipoint switch, firmware transfer).
- *The 38 settings* each have a row: who writes it in the app, whether the app reads it at connect, what the Buds answered in 80 logs, and what it
  is. The app writes 21 of them. It never reads seven (6, 8, 9, 10, 14, 20, 33) because its read loop skips exactly those. The code gave names to
  three settings that had none (5 = diagnostics sharing, 14 = eartip seal test running, 21 = "dosimeter notifications", the Volume level
  notifications switch) and confirmed two (3 = set-up finished, 6 = set-up mode).
- *Which product uses which settings list* is settled by the code: the Buds report a device type (the Pro 2 report 6, code name `LARGO`), and the
  app picks the settings list from it. The two other lists the project had found belong to device types 1 and 2 — other earbuds.
- *The UUID register* has a checked negative for all 19 UUIDs the captures show: none of them occurs anywhere in the app, in either byte order.

**3. Which open questions moved?** Of the 265 open questions the project carries, 72 are ones the app's code could say something about. Of those,
17 are answered, 28 are narrowed, 2 are confirmed, 1 is done, and 24 are unchanged (not worked, or not worth working — "Phase 1 inventory" says
which). The other 193 need a capture, a hardware test, or code that is not in this app (Google Play services, the Google app, the firmware,
Android); one of those moved because the code showed where it belongs. The answers that matter most:
- *The "unsolicited announcement" is not unsolicited from the app's side.* The app never asks for the software info; it opens a waiting call and the
  Buds' announcement completes it. The app then treats the announcing bud as its "primary" and talks on that bud's channel.
- *The EQ "navigate away" save* is a screen-change listener: leaving the EQ screen — Back, the arrow, or opening another screen — saves the curve when
  the Save button is enabled. Home does not. `TODO.md` now carries the exact test.
- *The slider that jumps about 10 s after a drag* is a 10-second throttle in the app's own screen code — display only.
- *The battery entry's second number is a charger type* (not charging / wired / wireless), not an "in the case" flag — in the app's words.
- *Find device* is not the app's own row. The app has an empty, hidden placeholder that Google Play services fills. Why it disappears is therefore
  not answerable from any version of this app.
- *Loud Noise Protection and Adaptive Audio* have no control and no command in this app version.
- *One earlier hypothesis is refuted:* "the ANC controller is absent" cannot explain the silent ANC taps of `CAP-051`; the controller is always there.

**4. What could not be answered from this app version?** What settings 1, 8, 9, 10, 20, 23–26, 30, 31, 33–38 are (the app has no writer, no reader
and no name for them; seven of them the firmware itself answers with "unknown"), what setting 32 is (only Android's Settings screen can write it),
and setting 39, which only the newer app asks for. Everything
about the Message Stream, the battery advertisement, the "GSND" channels and the account key: there is no code for any of it in this app.

**5. What can the tools do now?** Check every citation in the documents against a decompiled tree in a few seconds (`citation_checker` — the first
thing to run on a new app version); name every service and method id found in the capture logs from the app's own strings (`pwrpc_name_table`);
find a text or setting key in the app's resources and follow it to the code that uses it (`structural_index strings`); resolve the type of every
plain sub-message field (`schema_batch_extractor`); and look up a UUID from a capture in both byte orders (`uuid_ble_context find`).

**What this session did not do:** no change under `android/` or `dist/`, no build, no ADR, no status change in `PROTOCOL.md`, no decompiled content
in the repository. Every 🟢 in this file is "this code exists and does this" or "these bytes are in the log"; what the Buds do with it stays 🟡.
