## Context (from the maintainer, not re-derived here)

The maintainer asked, in their own words (translated from Dutch, preserved in full below the
horizontal rule at the end of this prompt): create a prompt in `ai-sessions/` that (1) runs
`resolve-all` on `aie` and `esk` to look at every case and try to extract findings from that, then
answers (2) what is further needed to reverse-engineer the APK, (3) which items from
`reverse-engineering/tools/BACKLOG.md` should now be implemented further, and (4) which workflows
are needed for reverse-engineering the APK and which steps/scripts those workflows should contain.

**Why `aie` and `esk` specifically.** Both are R8-merged synthetic lambda-dispatcher classes
already known to sit inside `libmaestro`'s own `WriteSetting`/`GetSoftwareInfo` send pipeline
(`REVERSE_ENGINEERING.md`'s `qhr`/`fye` entry) — but only one discriminator value has ever been
manually investigated for each (`aie` discriminator `7`; `esk` discriminator `19`), out of 20 and
~20 real cases respectively. Every other case is, as far as this project's documentation shows,
**completely unexamined** — not because it was checked and found irrelevant, but because nobody
has looked yet. This is exactly the gap `lambda_dispatcher_resolver`'s `resolve-all` command was
built to close cheaply (`ai-sessions` chat session of 2026-09-16, `reverse-engineering/tools/lambda_dispatcher_resolver/SPEC.md` §5/§10's `resolve-all`
addition).

## Phase 1 — `resolve-all` on `aie` and `esk`; extract candidate findings

1. Run, from `reverse-engineering/tools/lambda_dispatcher_resolver/`:
   ```
   .venv/bin/python3 -m lambda_dispatcher_resolver.cli resolve-all \
     --apk-root ../../apk/v1.0.955078536-10253511 --class aie --output-dir /tmp/aie_all
   .venv/bin/python3 -m lambda_dispatcher_resolver.cli resolve-all \
     --apk-root ../../apk/v1.0.955078536-10253511 --class esk --output-dir /tmp/esk_all
   ```
   (Use whatever scratch location this session's own environment provides instead of `/tmp` if one
   is designated — the point is a location outside `reverse-engineering/apk/` and outside git, not
   the literal path.)
2. Read **every** resulting file for both classes — not a sample. For each case, record:
   - the discriminator value and `resolution_status`;
   - a one-line plain description of what the branch does (e.g. "casts `this.a` to
     `OtaApplyWorker`, checks connection state, calls `ftj.i(str).p()`") — mechanical description
     of the code, not an interpretation of protocol meaning yet;
   - whether the branch references any class/method/field already known to this project
     (cross-reference against `REVERSE_ENGINEERING.md`'s existing entries — e.g. does a case
     reference `fyv`, `fyo`, `qhr`, `ftj`, `gcl`, or any other already-catalogued class?) or
     something genuinely new;
   - for cases where `jadx.decompilable` is `false`, note that explicitly — do not skip a case just
     because only smali evidence exists (per `AGENTS.md` §13.6, an unexamined case is not the same
     as a checked-and-irrelevant one).
3. **Zero-creativity rule applies to this reading pass exactly as it does to a capture** (`AGENTS.md`
   §13.6): a case that references an unfamiliar class is an explicit 🔴 OPEN QUESTION ("case N calls
   `X.y()`, `X` not yet catalogued — not investigated further this pass"), not a guessed
   interpretation. Do not speculate about a case's Bluetooth-protocol relevance beyond what the code
   itself, plus this project's own existing catalogued classes, actually supports.
4. Produce a per-class table (all cases, not a sample) in the result file: discriminator value →
   one-line mechanical description → cross-reference status (already-known / genuinely new /
   open question) → whether it looks worth a follow-up trace.
5. For any case that looks like a genuinely new, potentially protocol-relevant finding (e.g. a
   previously-uncatalogued caller of `fyv.a(qjc)`/`WriteSetting`, or a reference to a class this
   project hasn't seen before in a Bluetooth-adjacent context), trace it one level further by hand
   (read the referenced class's own source) — but do not chase every tangent to full depth; flag
   what's promising and stop, recording the open question for a future session if full depth would
   blow this phase's own scope.
6. Write up confirmed, code-level findings (call-graph facts, not protocol claims) as proposed
   additions to `REVERSE_ENGINEERING.md`'s `qhr`/`fye` entry (for `aie`) and its own entry for `esk`
   — labeled per `PROJECT_RULES.md` §1, awaiting maintainer review per `AGENTS.md` §6/§15. Do not
   promote anything to 🟢 FACT in `PROTOCOL.md` or write a `DECISIONS.md` ADR.

## Phase 2 — What's still needed to reverse-engineer the APK further?

Using Phase 1's own result as one concrete data point (not the only one), and
`REVERSE_ENGINEERING.md`'s "Known limitations of this analysis" / "Candidate rich schemas outside
this pass's traced call graph" sections, `TODO.md`'s Phase 2 "Targeted research follow-ups" list,
and `PROTOCOL.md` §6's still-open items that trace back to APK code (e.g. `MaestroEndpointService`'s
Dagger-multibinding assembly site, DLCI 0x08's own identity) as the other inputs:

1. Inventory, explicitly, every currently-open APK-RE question this project has on record (do not
   re-derive from scratch — collect the ones already documented across the files above into one
   list here, with a pointer back to each source).
2. For each, assess: is this a question `lambda_dispatcher_resolver` could help answer directly (a
   lambda-dispatcher pattern), a question a *different* kind of tool would help with (see Phase 3),
   or a question that fundamentally needs a fresh capture/experiment rather than more static
   analysis (flag these as out of this prompt's own scope — no new Bluetooth capture is performed
   as part of this task)?
3. State plainly which of these is currently the single highest-leverage next static-analysis
   target, and why — this is a recommendation, not a decision this session makes unilaterally.

## Phase 3 — Which `reverse-engineering/tools/BACKLOG.md` items should be implemented next?

`reverse-engineering/tools/BACKLOG.md` lists six tooling ideas (general structural code index, UUID
+ BLE context reconstruction, limited dataflow, protobuf schema batch-extractor, wire-payload
auto-decoder, APK version-diff tool, tshark/DLCI-reassignment helper) plus a suggested-not-binding
priority order. Using Phase 1's actual experience running `lambda_dispatcher_resolver` for real
(what was easy, what was still manual and tedious) and Phase 2's own inventory of open questions:

1. For each `reverse-engineering/tools/BACKLOG.md` item, assess concretely: would it have measurably helped Phase 1 or any
   Phase 2 item go faster/deeper? Be specific — "yes, the general structural code index would have
   let Phase 1 find every *caller* of `aie`/`esk` automatically instead of requiring a manual
   `grep -rn "new aie("`" is the right level of concreteness; "this would generally help" is not.
2. Recommend an explicit priority order (which may or may not match `reverse-engineering/tools/BACKLOG.md`'s own existing
   suggested order — say so either way, with reasoning) — this is a proposal for the maintainer to
   approve, not a decision this session makes on its own.
3. For the single top-recommended item, sketch (not fully design — that's a future spec document,
   per `reverse-engineering/tools/BACKLOG.md`'s own "graduates out of this file by getting its own spec document" rule) what its
   first, narrowest useful version would look like, mirroring how `lambda_dispatcher_resolver`
   itself started narrow.

## Phase 4 — What workflows does APK reverse-engineering in this project need, and what should each contain?

Distinct from Phase 3's *tools* question: this phase asks about the *process* a researcher (human
or AI session) actually follows when doing APK-RE work in this project, end to end.

1. Read `APK_REVERSE_ENGINEERING_PROCEDURE.md` in full (already required in Phase 0) and describe
   the workflow(s) it already documents (pull → decompile → search → analyze, plus the
   diff-against-previous-version pass it names but doesn't yet implement).
2. Identify concretely where `lambda_dispatcher_resolver` fits into that existing workflow (e.g. as
   a new step whenever an R8-synthetic lambda class is encountered during the "search"/"analyze"
   stage) and propose the exact wording for that addition.
3. Identify any OTHER recurring workflow this project's own APK-RE sessions have repeated by hand
   across multiple sessions, that isn't yet named as its own documented flow (candidates to check
   explicitly, not an exhaustive requirement to invent more): "trace a wire-confirmed field number
   back to its APK write/read call sites" (the method `DECISIONS.md` ADR-019 established), "resolve
   an R8-synthetic lambda dispatcher" (now `lambda_dispatcher_resolver`'s own job), "cross-reference
   a newly-found class against the existing `REVERSE_ENGINEERING.md` catalog before writing a new
   entry" (to avoid re-documenting something already covered under a different name).
4. For each workflow identified (existing or newly named), list the concrete steps and, where one
   would help, which script/tool from `reverse-engineering/tools/BACKLOG.md` or already in `scripts/`/`reverse-engineering/tools/`
   supports that step — a flow with no tool support at a given step is a legitimate outcome
   ("step 3 is still a manual JADX read, no tool proposed for it yet"), not something to force a
   tool onto.
5. Write this up as a proposed addition to `APK_REVERSE_ENGINEERING_PROCEDURE.md` (a new section or
   amendment, not a wholesale rewrite) — proposed, not committed, per the same sign-off discipline
   as everything else in this prompt.

## Guardrails

- **Scoped to the companion app's own decompiled output only** (`reverse-engineering/apk/v1.0.955078536-10253511/`,
  or whatever version is actually on disk per Phase 0) — never Google Play Services, per
  `DECISIONS.md` ADR-025.
- **Never independently promote a finding to 🟢 FACT in `PROTOCOL.md`, and never write or alter a
  `DECISIONS.md` ADR, without explicit maintainer approval** (`AGENTS.md` §6/§15).
- **No assumptions, no sampling.** Every case `resolve-all` returns for `aie`/`esk` is read, not a
  subset; a case whose meaning isn't derivable from the evidence in hand is an explicit open
  question, not a filled-in guess (`AGENTS.md` §13.6).
- This is a research/tooling/documentation task — no new Bluetooth capture or hardware action is
  performed as part of this prompt (no new `CAP-NNN` session is created).
- `lambda_dispatcher_resolver` itself is not modified as part of this prompt unless Phase 1 finds an
  actual bug in it (in which case: fix it, add a regression test reproducing the bug first, exactly
  as its own SPEC.md and existing test suite already model).
