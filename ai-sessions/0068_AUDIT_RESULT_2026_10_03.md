## 2. Executive summary

**State of the project after 1.0.0.** The released app is what the documents say it is: the published APK is the tested APK (byte-identical to the kept build, tag on the build commit, signed, no `INTERNET` permission, exactly the minimal permission set), the build/test/lint gate is green (1,709 unit tests, 0 failures), every wire frame the app sends is byte-identical to a captured frame, and every write passes the Safe-Mode gate. The protocol knowledge the app relies on held up under re-derivation: of the frames re-extracted in this audit (several hundred, across the 60 analysed captures) none contradicts an implemented command.

**What is wrong, in order of weight:**

1. **Two protobuf readers can be made to throw or loop forever by one malformed length field** (`A68-APP-01`, critical). An inbound frame is untrusted data (`AGENTS.md` §6/§11: "must never crash"); the fuzz tests do not cover an oversized length varint, although §11 names it. Verified by running the decoders.
2. **The release rule "the Definition of done is ticked only with the capture's evidence" was not met for ANC** (`A68-GOV-01`): no capture contains an ANC `Set` sent by build 1.0.0; the tick rests on the maintainer's own test. The runbook was neither followed nor amended, and the code between the last ANC-verified build and 1.0.0 differs in 27 files.
3. **`DECISIONS.md` lost the heading of ADR-035** in a 0059 edit (`A68-DEC-01`); its body now reads as part of ADR-034. No lint catches it.
4. **Several documented "negatives" and counts are wrong**, and two of them carry open questions or FACT texts: `CAP-002` "no HFP traffic" is a filter artefact (`A68-CAP-01`), ADR-022's "17 occurrences in 10 captures" is 19 in 11 (`A68-PROT-01`), `PROTOCOL.md`'s "OFF direction not captured" for Multipoint and its single-sample head-gesture entry ignore frames already on disk (`A68-PROT-02/03`), the Ring "two ACK variants / retransmission" reading has the directions reversed (`A68-PROT-04`), and `CAP-066`'s "2 of 2" channel switch is 3 of 3 (`A68-CAP-02`).
5. **The app shows a stale ANC mode as current and can lose an ANC update** (`A68-APP-02/03`), **picks an arbitrary "Pixel Buds" device when no association exists and offers no way to pair replacement Buds** (`A68-APP-04/05`), and its release script's release-candidate version code is only right for `X.0.0-rc.N` (`A68-HK-01`).
6. **The documents carry a large amount of pre-release and superseded text** — `AGENTS.md` §10 still calls dependency injection undecided, `ARCHITECTURE.md` §9 describes a `BLUETOOTH_SCAN` declaration that does not exist, `TODO.md` is mostly a done-log, the capture FINDINGS accumulate dated layers under status banners — see §6.

**New protocol leads (section 5):** the unexplained `CAP-021` DLCI 0x0a burst is bracketed wave-by-wave by a DLCI 0x08 exchange (four sessions that look like Assistant voice queries); Multipoint OFF, head-gestures OFF and two more Volume-EQ writes exist in old captures; DLCI 0x08 `04 16` follows the head-gesture setting and `04 05` follows wear/Settable; the Fast Pair battery page does name a use-case trigger (case just opened) that no capture has tested.

**What to do first:** fix `A68-APP-01` with regression fixtures and a structured fuzz test and ship it as 1.0.1; restore the ADR-035 heading; run the outstanding ANC/tile/Bluetooth-off re-test on the release build and record it; correct the wrong FACT texts with the maintainer's approval; then a MAINTENANCE pass over the stale documents (section 6).

**A68-APP-01 · critical · error (crash / hang on untrusted input) · FACT (JVM), HYPOTHESIS (effect on the device).** Where: `android/data/…/codec/CaseBatteryFrame.kt:121` `if (len < 0 || next + len > data.size) return null` — `next + len` overflows `Int` for a length varint of 0x7FFFFFFF, the guard passes and `copyOfRange` throws; `codec/PwRpc.kt:152-154` — the same with `Long`, then `i = next + len.toInt()` moves the index backwards.
