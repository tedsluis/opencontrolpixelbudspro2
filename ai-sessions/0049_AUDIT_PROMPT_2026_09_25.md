If you find something you believe should be fixed, describe the fix precisely enough that a later session can apply it without re-deriving your reasoning — do not apply it yourself.

## 1. Objective

Perform a rigorous, exhaustive, end-to-end review of this entire project — documentation, protocol knowledge, architecture decisions, reverse-engineering findings, the `TODO.md` backlog, and the Android app's own development — and report every defect you can substantiate. This is a **quality/correctness audit**, not a feature-implementation session: nothing gets fixed here, everything gets found, explained, and handed off with enough detail that fixing it later is straightforward.

## 2. Scope

For every file and area in scope (§3), actively look for:

1. **Errors** — technical inaccuracies, logical mistakes, incorrect Bluetooth/Android knowledge, plain factual errors.
2. **Inconsistencies** — contradictions within a single file or across multiple files (e.g. a protocol detail that contradicts an architecture decision, or a rule in `PROJECT_RULES.md` that is violated elsewhere without acknowledgment).
3. **Improvements** — concrete opportunities to improve the architecture, documentation clarity, project structure, or reverse-engineering methodology.
4. **Incompleteness** — missing documentation, undocumented features, dangling references, or broken links.
5. **Ambiguities** — vague statements, poorly defined statuses, or unclear instructions that could plausibly cause a future contributor (human or AI) to misinterpret them.
6. **Impossibilities / unworkable plans** — architecture decisions, code plans, or protocol interpretations that are technically impossible, violate fundamental Android/Bluetooth constraints, or violate the "Zero-GMS" rule (`AGENTS.md` §1).
7. **Misplaced content** — information that belongs in a different file per the project's own structure (e.g. protocol specification detail sitting in `ARCHITECTURE.md` instead of `PROTOCOL.md`, or log analysis that is missing from its own `CAP-NNN-FINDINGS.md`).
8. **Undiscovered protocol findings** — actively investigate what hasn't been investigated yet. Look at the existing `captures/`, hex dumps, and protocol notes to find patterns, opcodes, frame envelopes, or correlations that have been overlooked or are not yet documented. Prioritize re-examining `PROTOCOL.md`'s own 🔴 OPEN QUESTION and 🟡 HYPOTHESIS entries against evidence that *already exists* in `captures/` but may not have been fully cross-referenced. Where you find a plausible missed pattern, opcode, frame envelope, or correlation, report it as a lead with the specific frame numbers/hex that support it — do **not** promote it to FACT or write it into `PROTOCOL.md` yourself (`AGENTS.md` §6).
9. **Architectural shortcomings** — evaluate the soundness of the application architecture, module division, separation of concerns, and dependency injection choices.
10. **Application (Android app) shortcomings** — both in the Kotlin source itself (such as bugs, state management gaps, threading issues, resource leaks, or test coverage defects) and in how well it reflects what `ARCHITECTURE.md`/`PROTOCOL.md`/`DECISIONS.md` actually specify.
11. **Search for the genuinely unknown** — an open-ended pass, not tied to a specific checklist item: what has nobody asked yet? Are there capabilities the official app or the protocol clearly supports that this project has never even logged as a `TODO.md` candidate? Are there `DECISIONS.md` ADRs whose consequences were never followed through?
12. **Deep re-review of the latest sessions**, specifically:
    - `ai-sessions/0045_MAINTENANCE_PROMPT_2026_09_24.md` / `ai-sessions/0045_MAINTENANCE_RESULT_2026_09_24.md`
    - `ai-sessions/0046_FEATURE_PROMPT_2026_09_24.md` / `ai-sessions/0046_FEATURE_RESULT_2026_09_24.md`
    - `ai-sessions/0047_CAPTURE_PROMPT_2026_09_25.md` / `ai-sessions/0047_CAPTURE_RESULT_2026_09_25.md`
    - `ai-sessions/0048_FEATURE_PROMPT_2026_09_25.md` (prompt only)
    Read all four sets in full and audit them with the same rigor as reference docs (categories 1–7 apply to session logs too, not just reference docs).

## 4. Strict execution rules

- **No assumptions.** Verify everything. Do not take project claims about standard protocols at face value just because they read as claims about a standard protocol.
- **Validate externally.** Use search tools to check claims against official documentation (Android Developer Docs, the Bluetooth Core Specification, the Google Fast Pair specification, etc.) whenever a claim rests on external, checkable ground truth.
- **No sampling.** This is not a spot-check. Perform a complete, exhaustive review of every file in scope (§3) — every detail gets checked, not a representative subset. (§2 item 8's raw-capture scoping note is the one deliberate exception, for feasibility reasons, and is spelled out precisely there — it does not license sampling anywhere else.)
- **Evidence traceability.** Apply the same standard this project applies to itself: every claim about a capture must trace back to a specific frame/timestamp; every claim about the app must trace back to a specific file and line; every claim about an external spec must cite the section you're relying on.
- **Industry-standard review methodology.** Structural-integrity checks (do headers/sections nest correctly, do cross-references resolve, does a table's own column definitions match its rows), traceability checks (per above), and consistency checks (the same fact stated the same way in every place it appears) all apply.
- **No file changes during the review.** This is assessment only — see §0's "writes nothing except its own result file(s)" rule.

## 6. Suggested phases (sequential; adjust only if you find a materially better grouping)

1. **Governance/compliance pass** — `AGENTS.md`, `PROJECT_RULES.md`, `PROJECT.md`: internal consistency, and — critically — whether the *rest of the project* actually complies with what these three files require (e.g. every `DECISIONS.md` ADR has the sign-off provenance `AGENTS.md` §6 requires; every `.proto`/schema reference matches §4's extraction-workflow assumption; no permission beyond §2's minimal set appears anywhere in the Android manifest).
2. **Protocol pass** — `PROTOCOL.md` end to end: internal consistency (does a later "Update" entry ever silently contradict an earlier FACT without flagging the conflict?), FACT/HYPOTHESIS/ASSUMPTION/OPEN QUESTION labeling correctness, and the undiscovered-findings investigation from §2 item 8.
3. **Architecture pass** — `ARCHITECTURE.md` end to end, cross-checked against the actual Android source tree: does the code actually implement what this document claims, module boundary by module boundary, feature by feature?
4. **Decisions pass** — every `DECISIONS.md` ADR: internal consistency, whether a later ADR properly supersedes an earlier one it conflicts with (vs. silently contradicting it), whether every ADR's stated "Consequences" were actually followed through in the code/docs, and cross-reference integrity with `id_registry.csv`.
5. **Backlog/housekeeping pass** — `TODO.md`, `CHANGELOG.md`, `id_registry.csv`, `ai-sessions/INDEX.md`: staleness, dangling references, items marked done that aren't (or vice versa), duplicate or conflicting entries.
6. **Capture-evidence pass** — every `captures/CAP-NNN-*` pair's `EVENT-NOTES.md`/`FINDINGS.md` (§3), plus the §2 item 8 investigation.
7. **Session-history pass** — the full `ai-sessions/` set for structural/registration consistency, with the deep full-text audit of the latest sessions (0045, 0046, 0047, 0048) specifically (§2 item 12).
8. **Application pass** — the Android source tree: architecture, error handling, test coverage, and code-vs-documentation fidelity (§2 items 9–10).
9. **Synthesis pass** — the open-ended "search for the unknown" (§2 item 11), plus final report assembly: deduplicate findings that surfaced in more than one phase, cross-reference them against each other, and produce the final structured deliverable (§8).

A comprehensive, clearly structured audit report (`ai-sessions/0049_AUDIT_RESULT_2026_09_25.md`, per the header/status conventions in `AI_SESSION_LOG_PROCEDURE.md` §4).
