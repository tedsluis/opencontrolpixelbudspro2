## 0. How to use this prompt

This is a **review-only** session: it produces a single structured findings report and touches no
other file. It is intentionally large and is expected to span multiple phases; it does not have to
finish in one context window (see §5's resumability rule).

**Read, in this order, before doing anything else** (`AGENTS.md` §0.1, binding per
`AI_SESSION_LOG_PROCEDURE.md` §8): `AGENTS.md` → `PROJECT_RULES.md` → `PROJECT.md` → `ARCHITECTURE.md`
→ `PROTOCOL.md` → `DECISIONS.md` (**every** ADR, not just the recent ones — you need the full decision
history to judge consistency) → `TODO.md`. Then `ai-sessions/INDEX.md` (the full session history, to
know what already exists and why), `CAPTURE_BLUETOOTH_HCI_SNOOP.md`, `TESTPLAN_BLUETOOTH_HCI_SNOOP.md`,
`REVERSE_ENGINEERING.md`, `id_registry.csv`, and `DESKRESEARCH_FINDINGS.md`.

**Follow every guardrail in `AGENTS.md` throughout**, most relevantly §6 (an audit may *propose* a
FACT promotion or an ADR — clearly labeled as a proposal for the maintainer — but must never write
one into `PROTOCOL.md`/`DECISIONS.md` itself) and §12/§13's evidence discipline (every claim about a
capture needs a frame number; every claim about the app needs a file:line reference). `PROJECT_RULES.md`
§1's evidence rules govern how you write findings: label every conclusion FACT/HYPOTHESIS/ASSUMPTION/
OPEN QUESTION exactly as that document requires — an audit report is not exempt from this discipline
just because it is a meta-review of other documents, and a finding that itself violates the evidence
rules while auditing for evidence-rule violations would undermine the report's own credibility.

**This session writes nothing except its own result file(s)** (`ai-sessions/0044_AUDIT_RESULT_2026_09_23.md`,
and, if the review naturally produces one, a structured findings artifact alongside it — but not by
editing `PROTOCOL.md`/`ARCHITECTURE.md`/`DECISIONS.md`/`TODO.md`/application source, etc. directly).
If you find something you believe should be fixed, describe the fix precisely enough that a later
session can apply it without re-deriving your reasoning — do not apply it yourself.

## 1. Objective

Perform a rigorous, exhaustive, end-to-end review of this entire project — documentation, protocol
knowledge, architecture decisions, reverse-engineering findings, the `TODO.md` backlog, and the Android
app's own development — and report every defect you can substantiate. This is a **quality/correctness
audit**, not a feature-implementation session: nothing gets fixed here, everything gets found,
explained, and handed off with enough detail that fixing it later is straightforward.

## 2. Scope

For every file and area in scope (§3), actively look for:

1. **Errors** — technical inaccuracies, logical mistakes, incorrect Bluetooth/Android knowledge, plain
   factual errors.
2. **Inconsistencies** — contradictions within a single file or across multiple files (e.g. a protocol
   detail that contradicts an architecture decision, or a rule in `PROJECT_RULES.md` that is violated
   elsewhere without acknowledgment).
3. **Improvements** — concrete opportunities to improve the architecture, documentation clarity,
   project structure, or reverse-engineering methodology.
4. **Incompleteness** — missing documentation, undocumented features, dangling references, or broken
   links.
5. **Ambiguities** — vague statements, poorly defined statuses, or unclear instructions that could
   plausibly cause a future contributor (human or AI) to misinterpret them.
6. **Impossibilities / unworkable plans** — architecture decisions, code plans, or protocol
   interpretations that are technically impossible, violate fundamental Android/Bluetooth constraints,
   or violate the "Zero-GMS" rule (`AGENTS.md` §1).
7. **Misplaced content** — information that belongs in a different file per the project's own
   structure (e.g. protocol specification detail sitting in `ARCHITECTURE.md` instead of `PROTOCOL.md`,
   or log analysis that is missing from its own `CAP-NNN-FINDINGS.md`).
8. **Undiscovered protocol findings** — actively investigate what hasn't been investigated yet.
   Practically, given dozens of existing `captures/CAP-NNN-*` directories, this means: prioritize
   re-examining `PROTOCOL.md`'s own 🔴 OPEN QUESTION and 🟡 HYPOTHESIS entries against evidence that
   *already exists* in `captures/` but may not have been fully cross-referenced, rather than attempting
   to re-parse every raw `btsnoop_hci.log` from scratch (infeasible in one session and not what this
   audit is for). Where you find a plausible missed pattern, opcode, frame envelope, or correlation,
   report it as a lead with the specific frame numbers/hex that support it — do **not** promote it to
   FACT or write it into `PROTOCOL.md` yourself (`AGENTS.md` §6).
9. **Architectural shortcomings.**
10. **Application (Android app) shortcomings** — both in the Kotlin source itself and in how well it
    reflects what `ARCHITECTURE.md`/`PROTOCOL.md`/`DECISIONS.md` actually specify.
11. **Search for the genuinely unknown** — an open-ended pass, not tied to a specific checklist item:
    what has nobody asked yet? Are there capabilities the official app or the protocol clearly supports
    that this project has never even logged as a `TODO.md` candidate? Are there `DECISIONS.md` ADRs
    whose consequences were never followed through?
12. **Deep re-review of the two most recent sessions**, specifically: `ai-sessions/0042_FEATURE_PROMPT_2026_09_20.md`
    / `ai-sessions/0042_FEATURE_RESULT_2026_09_20.md` and `ai-sessions/0043_FEATURE_PROMPT_2026_09_22.md`
    / `ai-sessions/0043_FEATURE_RESULT_2026_09_22.md` — read both pairs in full and audit them with the
    same rigor as everything else (categories 1–7 above apply to session logs too, not just reference
    docs). `ai-sessions/0043`'s own `RESULT` file documents, in its §1, a serious process incident from
    that session (a background subagent that went outside its instructions and fabricated an approval
    citation before being caught and corrected) — verify that incident's own resolution is actually
    consistent (the corrected `DECISIONS.md` ADR-037/ADR-038 process notes, the `CAP-059-EVENT-NOTES.md`
    data-loss note, and every file that session touched) rather than taking the RESULT file's own
    account of "corrected" at face value.

## 4. Strict execution rules

- **No assumptions.** Verify everything. Do not take project claims about standard protocols at face
  value just because they read as claims about a standard protocol.
- **Validate externally.** Use search tools to check claims against official documentation (Android
  Developer Docs, the Bluetooth Core Specification, the Google Fast Pair specification, etc.) whenever
  a claim rests on external, checkable ground truth.
- **No sampling.** This is not a spot-check. Perform a complete, exhaustive review of every file in
  scope (§3) — every detail gets checked, not a representative subset. (§2 item 8's raw-capture scoping
  note is the one deliberate exception, for feasibility reasons, and is spelled out precisely there —
  it does not license sampling anywhere else.)
- **Evidence traceability.** Apply the same standard this project applies to itself: every claim about
  a capture must trace back to a specific frame/timestamp; every claim about the app must trace back to
  a specific file and line; every claim about an external spec must cite the section you're relying on.
- **Industry-standard review methodology.** Structural-integrity checks (do headers/sections nest
  correctly, do cross-references resolve, does a table's own column definitions match its rows),
  traceability checks (per above), and consistency checks (the same fact stated the same way in every
  place it appears) all apply.
- **No file changes during the review.** This is assessment only — see §0's "writes nothing except its
  own result file(s)" rule.

## 5. Resumability

This audit is expected to run across multiple phases (§6) and may not fit in a single context window.
Follow `AI_SESSION_LOG_PROCEDURE.md` §5: do **not** start a new numbered session to continue — keep
writing into the same `ai-sessions/0044_AUDIT_RESULT_2026_09_23.md`, appending each phase's findings as
it completes, and set the header's `Status` field to `partial — resumed` if the session is interrupted
before all phases finish (updating it to `complete` once they do, per `AI_SESSION_LOG_PROCEDURE.md`
§4). Before resuming, re-read this prompt file and the result file's own progress-so-far to avoid
re-doing a finished phase or silently skipping one.

## 6. Suggested phases (sequential; adjust only if you find a materially better grouping)

1. **Governance/compliance pass** — `AGENTS.md`, `PROJECT_RULES.md`, `PROJECT.md`: internal consistency,
   and — critically — whether the *rest of the project* actually complies with what these three files
   require (e.g. every `DECISIONS.md` ADR has the sign-off provenance `AGENTS.md` §6 requires; every
   `.proto`/schema reference matches §4's extraction-workflow assumption; no permission beyond §2's
   minimal set appears anywhere in the Android manifest).
2. **Protocol pass** — `PROTOCOL.md` end to end: internal consistency (does a later "Update" entry ever
   silently contradict an earlier FACT without flagging the conflict?), FACT/HYPOTHESIS labeling
   correctness, and the undiscovered-findings investigation from §2 item 8.
3. **Architecture pass** — `ARCHITECTURE.md` end to end, cross-checked against the actual Android
   source tree: does the code actually implement what this document claims, module boundary by module
   boundary, feature by feature?
4. **Decisions pass** — every `DECISIONS.md` ADR: internal consistency, whether a later ADR properly
   supersedes an earlier one it conflicts with (vs. silently contradicting it), whether every ADR's
   stated "Consequences" were actually followed through in the code/docs, and cross-reference integrity
   with `id_registry.csv`.
5. **Backlog/housekeeping pass** — `TODO.md`, `CHANGELOG.md`, `id_registry.csv`, `ai-sessions/INDEX.md`:
   staleness, dangling references, items marked done that aren't (or vice versa), duplicate or
   conflicting entries.
6. **Capture-evidence pass** — every `captures/CAP-NNN-*` pair's `EVENT-NOTES.md`/`FINDINGS.md` (§3),
   plus the §2 item 8 investigation.
7. **Session-history pass** — the full `ai-sessions/` set for structural/registration consistency, with
   the deep full-text audit of `0042`/`0043` specifically (§2 item 12).
8. **Application pass** — the Android source tree: architecture, error handling, test coverage, and
   code-vs-documentation fidelity (§2 items 9–10).
9. **Synthesis pass** — the open-ended "search for the unknown" (§2 item 11), plus final report assembly:
   dedupe findings that surfaced in more than one phase, cross-reference them against each other, and
   produce the final structured deliverable (§8).

## 7. Exclusions

**Privacy is out of scope for this audit's findings.** Do not scan for, flag, or report on
privacy-related data such as leaked MAC addresses, email addresses, names, or other personal
identifiers — ignore this category entirely. Real device identifiers in `captures/CAP-NNN-*` are the
maintainer's own already-made, informed decision (`DECISIONS.md` ADR-010); this is not new territory
for this audit to re-litigate. (This exclusion covers the *audit's own findings scope* — it does not
license ignoring `AGENTS.md`'s actual operational guardrails, e.g. if this review happens to notice
something genuinely novel and outside ADR-010's already-settled precedent — such as a different kind of
personal-data exposure a prior session hasn't already reviewed — a brief, single-line flag is
appropriate; a full privacy audit is not what this session is for.)

## 8. Deliverables

A comprehensive, clearly structured audit report (`ai-sessions/0044_AUDIT_RESULT_2026_09_23.md`,
per the header/status conventions in `AI_SESSION_LOG_PROCEDURE.md` §4). Group findings logically —
by the categories in §2, or by file/area, whichever reads more usefully once you see what you've
actually found; state which grouping you chose and why. **For every finding, include:**

- The exact file and location (line number/section, or a frame number for a capture-based finding).
- Why it's a problem — which of §2's categories it falls under, and the reasoning.
- A concrete, actionable recommendation for how to fix or resolve it — specific enough that a later
  session could act on it without re-deriving your reasoning.
- External evidence or documentation supporting the finding, where applicable (cite the source: a URL
  and section, or the Bluetooth Core Spec's section number, etc.).

Rank or flag severity where it's meaningful (e.g. "blocks correct operation" vs. "a documentation
clarity nit") so the maintainer can triage rather than having to weigh 200 undifferentiated items
equally.
